# DroneLinkServer operations

Status: source-derived; runtime/hardware not verified for this documentation baseline. Reviewed: 2026-11-05.

1. Install a compatible Node.js/npm environment; run `npm ci` in this repository. Serial-port dependencies may require host support. Verified runtime versions remain an M1 deliverable.
2. Set the hostname-specific `config.json` entry: node ID, explicit release directory (`releaseDir`), log path, telemetry serial port, domain ID and domain API key. Missing/invalid release selection starts with warnings and disables release features; the old `firmwarePath` is ignored with migration guidance. Startup creates missing skeleton entries and exits for missing host configuration. Do not commit actual keys.
3. Start the gateway using `node index.mjs`. It provides a terminal UI and serves the legacy web interface. UDP uses port 8007; inspect `index.mjs` for web port selection. Ensure the configured serial device and local network are accessible.
4. Start the independent hosted backend at the currently hard-coded forwarding destination `http://localhost:8003` if testing ingestion. M1 will make this configurable.
5. Simulation: `npm run sim`, with suitable `sim.json` and gateway connectivity. Do not assume a simulation pass proves firmware hardware behaviour.

Root `npm test` remains a placeholder failure. Select the explicit protocol and release suites below. The old sibling-source `parseModules.js` is retired; metadata is exported by DroneNode and help is rendered during explicit Server release preparation. Firebase deployment is a separate, unverified path; do not deploy it merely because `functions/` exists.

## SEP-07 physical workbench preservation — 2026-11-06

The bounded [SEP-07 plan](../../DroneLinkDatastore/docs/planning/sep-07-bench-preservation.md) owns current physical acceptance and companion identities. Use a separate gateway working directory and hostname configuration, an explicitly verified prepared release and no cloud credentials for local bench checks. Do not point the binary serial adapter at the USB console: this bench uses UDP for mesh telemetry. Observe current mesh addresses before choosing the gateway address, and reconfirm the physical node before active exchanges. A quiet passive sample is not proof of domain-wide address availability.

Physical checks found that `DroneLinkState` discarded the socket supplied by `observer.js` and its receive listener was commented out: the real browser remained at “Waiting for nodes” despite live gateway messages. Its optional constructor socket now feeds live observations through the existing state/discovery/raw-event path; playback still ignores live traffic, and direct no-socket construction remains supported. `node --test tests/live-state.test.mjs` failed against the old code and passes with the fix. Root `npm run test:protocol` includes this regression. This restores existing gateway behavior without introducing the shared-Client WB implementation.

Through the actual gateway, node 11 supplied live Management/UDP/NMEA data and three node files were downloaded privately before writing. Two versions of a new harmless support file were uploaded and read back; a separate Management Restart reset uptime and preserved that file. The temporary file was deleted and all three original files matched their pre-test hashes. An initially short post-upload uptime probe timed out; a later observation confirmed continuing uptime, so a timeout is not interpreted as an implicit restart. Actual Chrome rendering, reconnect and reload checks are distinct from the release suite's simulated hardware checks. Firmware programming and final source identities remain recorded in the owning plan.

The legacy `/routes` HTTP handler attempts to serialize circular runtime objects once a physical route exists and returns an error. This is an existing diagnostic endpoint issue; the browser's `getRoutes`/`route.update` socket path remains usable. It is a recorded follow-up, not evidence that the HTTP route inventory works. Node files/captures/full-flash backups remain private and are not repository fixtures. The upload implementation uses `/backup.txt` as temporary scratch storage: preserve/inventory files first and do not use an existing scratch file as a harmless test target.

Verify docs from this repo with `python3 ../DroneLinkDatastore/tools/check_docs.py`. Runtime checks and packet/command smoke gates are defined in the central M1/M2 plans.

## SEP-01 protocol checks — 2026-11-05

Install from the committed lockfile and local `vendor/dronelink-protocol-0.1.1.tgz` archive. The browser ESM artifact is already checked in; a normal startup/build does not rewrite it. Use `npm run protocol:check`, `npm run test:protocol` and `npm run test:protocol:browser`. The last command uses Node's experimental VM modules to evaluate the actual browser module graph without Node globals; it is not a real-browser UI test. Gateway replay intercepts all cloud requests and disables background timers.

For a deliberate version update, copy the reviewed archive, update its exact dependency/lockfile, the version-specific codec import and sync-script assertion, then run `npm run protocol:sync`. It writes only this checkout. Run equality, codec, gateway and browser checks before rollout. Use the central [release and rollback instructions](../../DroneLinkDatastore/docs/operations.md) and [SEP-01 evidence](../../DroneLinkDatastore/docs/planning/sep-01-protocol-compatibility.md). Reverting the whole pre-adoption codec also restores the known uint32 encoder bug.

Clean `npm ci --ignore-scripts` and these software checks passed; native serial dependencies, physical Wi-Fi/serial and complete gateway/UI startup were not exercised. This historical SEP-01 evidence predates SEP-05 replacement of the sibling-dependent firmware/module-generation tools.

## SEP-04 hosted installation and acceptance

The hosted service is an independent installation under `hosted/`. Follow its [runbook](../hosted/README.md): `cd hosted`, `npm ci --omit=dev`, then `npm start`. Missing hosted-root `config.json` produces its own skeleton and exits. Configure MongoDB/Google/session/Mapbox and an explicit verified Client release directory. Never copy the gateway hostname config into hosted. Relative artifact paths now resolve against `hosted/`; explicitly translate old service-relative paths during migration. The old Datastore server remains available through its retained Git revision for rollback, not through a second maintained runtime copy.

For tests, install dev dependencies, run `npm run test:mongo:prepare` explicitly, then `CLIENT_BUILD_DIR=<verified build> npm run test:application` and `npm run test:integration` with the same artifact input. The runner is pinned MongoDB 8.0.34 via `mongodb-memory-server-core` 11.3.0; the core package has no download hook. Tests launch their own loopback process and temporary DB path, reject arbitrary external database URI overrides and disable runtime downloads. `.cache/` is local/ignored. Real data/Google credentials are never test inputs.

Hosted pins `vendor/dronelink-persistence-0.1.2.tgz` in its own manifest/lockfile. New adoption explicitly copies a reviewed immutable release, updates both pin/lock, and reruns storage/API/compatibility/rollback gates. Normal install/start never updates sibling files or publishes/deploys. Production `npm ci --omit=dev` omits runner/original-schema test dependencies; production imports have no gateway/native/terminal requirements. Root `npm test` remains the legacy placeholder; hosted tests are selected from the hosted package.

SEP-04 completion companions: hosted implementation `975651f`, Datastore cutover/evidence `b288660`, persistence release evidence `e006d37`. This follow-up updates source/service paths only; tested hosted runtime bytes are unchanged. Broader live/provider/browser/hardware and generated-artifact gates remain separate.


## SEP-05 explicit release handoff

Obtain clean-source DroneNode firmware and metadata exports with adjacent `.sha256` files. In a clean committed Server checkout, run `npm run release:prepare -- --firmware <firmware.tgz> --metadata <metadata.tgz> --output <new-release-directory>`; preparation requires Python 3 for bounded archive extraction and uses the existing locked Mustache renderer. Renderer/template/guide/tool inputs are compared against committed Git blobs even when index flags hide edits. It verifies kind/schema, checksums, exact file sets, source/metadata matching and supported board, then renders help and publishes a complete new directory. It never invokes PlatformIO, selects a device or changes startup configuration. `npm run release:verify -- <release-directory>` checks the result independently.

Set your hostname entry's `releaseDir` to that directory, relative to the Server root or absolute, and restart the gateway. No release is selected implicitly from the old public assets. `firmwarePath` is obsolete and cannot override the selected image. Missing/invalid release starts the gateway with persistent browser/terminal warnings, HTTP 503 for release assets, and disabled distribution/catalog features. Telemetry, diagnostics and independent raw node/file operations remain usable. Fix or select a valid prepared directory and restart. Keep previous directories for rollback; do not edit the active directory in place. The VSC IP and VSC Upload actions are removed; develop/build/upload directly in DroneNode instead.

Run `npm run test:release` for disposable archive/preparation/HTTP/terminal/startup checks. To replay startup against an actual prepared artifact, supply `DRONELINK_RELEASE_DIR=<verified-release-directory>`; corruption checks modify only a private copy of that directory. Gateway startup tests replace only physical serial/UDP connections and select an ephemeral loopback port through a test-only module loader; they use synthetic configuration, never the user's config. Run `npm run test:release:browser` with Playwright available and installed Chrome. A desktop-bundled Playwright may be selected through `DRONELINK_PLAYWRIGHT_MODULE=<absolute module directory>`; `DRONELINK_BROWSER_CHANNEL` defaults to `chrome`. No browser download occurs. The test-only jQuery 3.6.0 fixture preserves its license header and is verified against the integrity digest already pinned in `observer.htm`.

Browser checks execute actual release UI and catalog consumer modules/Management controls with local fixture connections; Firebase module imports and device diagnostics are intercepted, and the draggable presentation plugin is inert. They check complete consumer import availability, valid/missing/invalid/rollback pages, persistent warnings/disabled catalog controls, actual state-code telemetry decoding, raw-file completion and Network diagnostics, plus a page kept open through changed gateway status. They do not claim full legacy application layout/interaction parity. No real account, serial device, UDP device, flash or filesystem upload is contacted. New valid selection after reconnect requires a deliberate browser refresh so unsaved drafts remain available to save. Shared [artifact contract](../../DroneLinkDatastore/docs/contracts/firmware-releases.md) and [SEP-05 plan/evidence](../../DroneLinkDatastore/docs/planning/repository-separation.md#sep-05-proposed-plan--2026-11-05) own behavior and completion scope.
